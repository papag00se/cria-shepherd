## Resource evidence and limits

The pinned architecture has a 512-wide encoder with 19 layers and two 512-to-2 heads. Source-derived tensor arithmetic, independently confirmed by CPU-only meta-device constructors, gives **68,144,640 encoder parameters plus 2,052 head parameters**. An FP16 encoder with FP32 heads projects **136,297,488 tensor bytes**, before serialization/constants. This is a planning calculation, **not a measured compliant export**. All required graphs, heads, embedding tensors, shards, constants and distinct backbones must actually total **less than 250,000,000 bytes**. The published 273,868,198-byte training checkpoint is not a compliant serving artifact and is not presented as one.

FP32 model/gradient/two Adam moments project about 1.09 GB, with an additional BF16 autocast-copy allowance. Attention workspace and allocator overhead are separate; whole-layer checkpointing and microbatch one are specified. The resource record gives component arithmetic at both the measured admitted maximum and the full native window, plus explicit proposed host/GPU/disk ceilings. Those ceilings are not measured peak memory or promises about availability. No `nvidia-smi`, CUDA allocation, device query or GPU profiling was used. An initial constructor attempt stopped at missing Torch before any model existed. A dedicated isolated **CPU-only** environment was then provisioned with Torch `2.8.0+cpu`, Transformers `5.20.2` and Tokenizers `0.23.3`. Meta-device constructors successfully confirmed every parameter count without loading pretrained weights, supplying inputs, running a forward call or allocating GPU memory; the CPU build has no CUDA runtime. Its package lock and proof are bound in the resource/release records. This verifies constructor compatibility only, not training or serving execution.

After **separate explicit authorization**, an isolated training environment, verified checkpoint, reproducible trainer/export implementation and measured resource/CPU parity checks are required. A recipe is not an implemented trainer. Stop an unsupported/OOM arm rather than silently changing precision, length, batch policy, backbone or input content. FP16 CPU operator support, RSS, latency and decision parity remain unmeasured. An INT8 export is a separately frozen comparison, not an automatic fallback. No deployment operating threshold or acceptable error trade-off has been approved. The pinned Torch CPU path is an offline in-process reference/prototype proposal, not permission to add a production dependency. Cria's stdlib-only runtime contract remains in force; a compatible production engine/dependency design is a separate unresolved gate. Privacy/provenance holds are accounting records, not a prediction panel; serving-only RSS/latency must be measured separately from the larger floating reference.
