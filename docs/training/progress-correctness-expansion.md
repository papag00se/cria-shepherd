# Progress correctness: family inventory and expansion

This is the original prospective family inventory, not a current count of authored projects, examples or labels. The names below were assigned to TRAIN **before** any proposed variants were authored. Some have since been authored, some remain proposals, and more families have been added; see [dataset progress](progress-correctness-dataset.md) and the private working report for current counts. Semantic overlap remains a review question, and a duplicate is redesigned or removed rather than counted as another project. A family is a coherent independent seed project with its own functionality and requirements, not a renamed file, port, language translation, generator seed or defect. Siblings, ports and transformations stay together. A project with too few sound requirements need not be padded to ten.

## Continuous construction principles

- Build each seed as a coherent runnable small project with real entry points and more than one meaningful responsibility, then select requirements appropriate to that project. Ten individually authored groups can share a project but should exercise different behavior and files; record common family ancestry and do not pretend they are independent projects. Preserve a separately maintained project/source registry and check conceptual overlap, not only names.
- Vary **workspace states**, not just wrong operators: edit existing code, add new files, delete obsolete files or APIs, modify and delete across files, wire libraries into real entry points, update schemas and consumers together, implement storage transitions, and include explicitly requested tests. Some groups should show partial multi-file migration or a correct implementation with missing tests. A deletion can be evidence only when the removed code is shown in full. Nothing may depend on an unchanged helper absent from the classifier input.
- Include naturally larger complete diffs from real coherent work: related source changes, independently valuable unrelated features, configuration, test additions, and realistic pre-existing context. Distribute unrelated changes across labels and include both unchanged and meaningful nonempty NOT_STARTED examples. No artificial comments or padding; no stage names in paths or model-visible text. Match the actual runtime evidence contract and report where a synthetic full-context diff differs from the legacy abbreviated renderer.
- Produce sensible multi-clause requirements with independently specified observable expectations. Derive oracle cases by hand from requirements, not generator output; capture ordinary successes and the consequential intended miss separately. Avoid task labels, tests written to approve the defect, single-token signatures, unobservable performance/concurrency claims, and false confidence from seed code. Include correct unconventional algorithms and semantics-preserving alternatives in the same split; use independent spot review where it is useful, without an approval pause.
- Track per-family, language, source, defect and split counts; group-aware rendered-input length distributions; actual execution and toolchain omissions; exact input collisions including old TRAIN; and near-duplicate candidates for semantic review. Lexical similarity is not a truth oracle. Review duplicate candidates without allowing TEST contents into selection or tuning. Report exclusions and unresolved ambiguity explicitly.
- Continue diverse TRAIN/DEV construction, practical fixture execution and evidence-led corrections; prior pilot and expansion blind reviews are provenance, not required review gates. Do not use held-out results to select examples, bug distributions, prompts or other decisions. The historical dictation/retrospective replay remains a separate preserved pool. Actual target totals are 3,000 TRAIN, 600 DEV and 600 newly authored TEST examples, not 3,000/600/600 claims about independent projects.
