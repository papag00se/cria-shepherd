# Multipart reads and retained private state

The canonical home for two connected things: how cria reads a large file through successive harness shell calls (the multipart bridge), and what private state that leaves on disk and who may delete it. [Image sessions](image-workflow.md) keep their own state under the same retention rules.

## Multipart reads

cria cannot read the coder's files itself (principle 23c). A file too large for one tool result is read as a series of lowered shell calls that the HARNESS runs; each page returns one checked record, and cria reassembles the bytes. It needs a harness that can execute successive shell calls and return their paired results.

**Session identity.** A stable, unique `X-Cria-Session-Id` (Chat Completions) or `prompt_cache_key` (Responses) names a conversation. Without one, cria correlates the calls it issued through a private durable index; it never assumes identical task text identifies a session. Ambiguous or unavailable state is not credited as a read. State lives under `~/.cria/multipart`.

**Credit.** A read earns read credit only when its final full model request was measured and delivered (an unknown fit keeps the received carriers without credit; a measured overflow withholds the encoded transport pages and tells the coder the file's size and how to read it in narrower pieces, also without credit). A prior image observation gives no read credit.

**Atomic with respect to writers.** The first page command reads the source once (one descriptor, `fstat` before and after, length checked against the size). When the stream needs more pages it copies those very bytes into a private snapshot (`snap`, plus `meta` holding the identity taken) inside an authenticated owned directory `.ctx-mpsnap-<token>` under the harness's own `$TMPDIR` (`ownedfiles.DIRECTORY_PROGRAM`, shared with the edit-sequence and gate scratch), re-reads the copy through its owned name and compares its digest with the bytes it was written from. Every later page is served from the snapshot, never from the path, so the logical read is exactly the file as of the first page whatever a writer does between pages (rewrite in place, append, truncate, replace by rename, change and revert). A snapshot altered in place changes the digest each page reports, and the consumer, which compares every page's source and stream digests with the first page's, fails the read closed as unverified.

Each page record carries a typed `snapshot` object: `mode` (`snapshot` or `live`), `reason` (`over_cap`, `unavailable` or none), `taken` (device, inode, size, mtime_ns when the snapshot was taken) and `now` (the path's identity as of that page). If the identity at the LAST page differs from the one taken (or the path is gone), the read is still delivered as the first page's exact bytes but labelled `⟦ctx:read-source-changed⟧` (`prompts/multipart_source_changed*.txt`: the file changed after the read began, what it is now, read it again before relying on or editing it). The label rides after the record, so the result earns no read credit and no protected-read fact (never current). A change that restores the mtime as well leaves identical bytes under an identical identity and is not reported: the delivered bytes are then the file's.

The page that carries the last extent removes the snapshot; an abandoned read leaves it. A re-run first page replaces its own earlier snapshot. A source larger than `filecommands.MULTIPART_SNAPSHOT_MAX_BYTES` (four times `windowcaps.REFERENCE_WINDOW`, the bytes the reference window holds at the repo's chars/4 estimate: a larger file cannot be delivered whole to that window anyway), or a snapshot that cannot be made (unwritable `$TMPDIR`), is paged live with the typed reason in the record: the older hash- and metadata-checked, detect-and-fail-closed behaviour, which cannot see a change-and-revert. The identity comparison happens when the last page runs, not when the model reads the result. Reflink (`FICLONE`) is not used: the first page's bytes are already in hand from the one descriptor.

**A chatty login shell.** The page record is found among whatever else the harness's shell printed; the noise is measured, later pages are sized to it, and a page that arrives cut is asked for again smaller (`multipart.py`, `tests/read_multipart/test_read_multipart_noise_shell.py`).

## Retention: nothing is deleted unless the operator says so

There is no trusted session-close authority. This was measured, not assumed: real Codex (pinned 0.159.3, `exec` and the TUI) sends no request at exit, `/clear` (the next turn simply carries a new `session-id`/`thread-id`; the old one is never mentioned again), `/quit`, SIGINT/SIGTERM cancel (the connection just drops) or compaction (an ordinary `POST /v1/responses` with `request_kind: compaction`, the same `session-id`, an incremented `window_number`); Chat Completions clients can only supply `X-Cria-Session-Id`, a name with no close semantics. So retained private resources are not deleted on request end, model completion, cache eviction, compaction or idle timeout. Operator call captures and backend caches have separate retention. Deletion authority is the OPERATOR's, in one of two forms that share one selection and removal implementation (`cria/retention.py`).

**1. The explicit command** (default: nothing is deleted).

```bash
python -m cria.retention list  [--kind multipart|image|snapshot|transient|all] [--tmp DIR] [--json]
python -m cria.retention prune [--kind ...] [--tmp DIR] [--older-than 14d] [--session ID] [--apply]
```

`list` shows every retained entry (size, age by last touch, state, kind). `prune` is a dry run unless `--apply`, and needs `--older-than` and/or `--session` so a bare invocation can never select everything. `--kind snapshot` (never part of `all`; it scans the shared harness temp directory, `--tmp` or `$TMPDIR`, not cria's home) lists and removes the `.ctx-mpsnap-*` directories (and `.cria-mpsnap-*`, the name earlier releases gave them) that abandoned reads leave, and only a directory of exactly that name shape, owned by this user, mode 0700, holding nothing but `.owner`, `snap` and `meta`. `--kind transient` (same rules, same temp directory, never in `all`) sweeps the credentialed scratch directories killed lowered programs leave: `.ctx-done-*`, `.ctx-edits-*`, `.ctx-private-*` and the earlier `.cria-done-*`, `.cria-edits-*`, `.gate-private-*`. Never a prefix sweep: a directory is removable only if it is owned by this user, mode 0700, and its own `.owner` certificate names exactly that prefix, credential and inode, and it holds nothing but regular files (the gate's `aux/` may also hold plain files and directories); the inode and certificate are checked again at removal.

**2. A standing instruction.** Set `[retention] auto_prune_after = "14d"` (minimum `1h`; default unset = off; optional `auto_prune_every`, default `1h`, minimum `1m`; both `<n><s|m|h|d|w>` strings) and cria runs `prune --apply --older-than` on `multipart` and `image` state itself, once at start and then on that cadence, from a background daemon thread. It is the operator's configured age, not cria's inference of closure. Source snapshots in the shared temp directory are never pruned automatically.

**Safety (both forms).** Image sessions are removed through the store's own closed-seal path (seal outside the payload, payload, seal last); multipart state through its own lock file (session record first, then call associations, so an interrupted run leaves only associations that fail closed). A live cria process holding an image session or the multipart lock is skipped; corrupt entries are removed only when selected by `--session` (never automatically); symlinks and unrecognized names are never touched; an interrupted run is retried by running it again. `prune --older-than` does not open or validate an image session younger than the age (it could not be selected); a `--session` prefix that names more than one entry and no entry exactly is refused with the candidates listed (give the full id). A session's workspace-image read provenance is an append-only `workspace-reads.log` in its directory (an earlier release's whole `workspace-reads.json` is still read as the base), held in memory and re-read only when the file is not the size this process left. The auto-prune releases the multipart lock before touching images, logs one `retention.auto_prune.removed` / `.skip` / `.failed` event per entry (a skip is announced once per process), and cannot raise into request handling (a failure is contained and logged as `retention.auto_prune.error`).

**What pruning means for a conversation.** A request in flight against pruned state gets the existing typed unavailable path, never a fabricated read: removed multipart continuations yield the unverified/unavailable note and removed image sessions are not restorable. Choose an age longer than any conversation you intend to resume. These checks catch mistakes, not an adversary: any process running as the same user can forge or delete these files.
