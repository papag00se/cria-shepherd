## Instrument fixes made during the baseline arm

The baseline arm doubles as the shakedown (`docs/battery-goal.md`). Three faults surfaced, all in
the instruments rather than the models, and all three had been silently scoring runs wrong.

- **`shipping-rates-py` verify.py demanded byte-identical seed tests** while its own prompt says
  "Add it, with tests". Adding the tests the task asks for was scored as tampering. Replaced with
  per-function AST integrity — the seeded test functions must survive unmodified, new ones are
  free. Re-proven against both cheats it was there to catch. gemma4's true score was 4/4, not 3/4.
- **cria parsed XML tool-call arguments in the wrong order.** `extract_json_object` ran before the
  `<parameter=…>` tags, so a dict literal appearing anywhere in an `edit_file` payload became the
  call's arguments. qwen35 scored 0/4 against an untouched workspace. Tags now win over a JSON scan
  of the same text.
- **The health wait was five minutes.** A cold 27B ternary-bonsai looked dead, the run raised before
  writing a result row, and the driver re-queued the same cell forever. Now fifteen minutes, plus a
  no-progress halt so an unwritten row stops the queue instead of looping it.

## Notes on the baseline results

- **gemma4 needs no assists on these two tasks** — 4/4 on both, unaided, in 15 and 46 calls. Worth
  stating plainly before the CRIA arm runs: on work this size the interesting question is whether
  the assists can avoid making it worse, not whether they help.
- **qwen35 emits its XML dialect in roughly 70% of calls** — 115 of 163 on `orders-api-py` were
  recovered from the reasoning channel, none rejected. Dialect recovery is load-bearing for this
  model in BOTH arms, which is why `docs/battery-goal.md` keeps it in the baseline.
- **qwen35's 1/4s are genuine.** On `orders-api-py` it worked the full 31 minutes, edited `app.py`
  and `db.py` and wrote `tests/test_http.py`, and landed only the SQL-injection fix. Real work,
  wrong results — not a lost-call artifact.
- **nemotron-elastic reaches for tools that do not exist.** It called `view_image` on a `.py` source
  file, then emitted `<function=str_replace_editor>` — a tool name from a different harness's
  vocabulary, not on the menu. cria correctly refuses to dispatch a tool that was never offered, and
  the turn ends empty. This is the same class of fault that retired it from the ladder; its zeros
  are evidence about the model. Whether an off-menu name should come back as a tool error rather
  than an empty turn is a real question, but it is a CRIA-arm question and must not be touched
  mid-arm — one run per code state.
