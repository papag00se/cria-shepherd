# Phi4 historical context and handoff integrity

**Status:** Investigation, 2026-11-07. Selected-boundary analysis, not a full reasoning walk or a representative prevalence study. No model replay, network, GPU, or service change was performed for this census. The operational observations and candidate status below include information supplied by the campaign owner; they are explicitly distinguished from the original boundaries inspected here.

## Question and limits

Does Phi4's smaller context window increase compaction pressure, lose history, and explain historical zero-usefulness results? The captures show concrete handoff and action-integrity problems, including a handoff that redefined the task and a coder action following it. They do **not** establish that the smaller window caused these problems, or how often they occurred across historical zeros. A matched-window trial with the same task, revision, harness and sampling would be needed to isolate window size; even that would measure outcomes across runs rather than attribute a single action automatically.

The authoritative inventory was read through `suite.results_store.read_rows()`. At the inventory snapshot there were 115 unique `phi4` run IDs, including 56 rows scored zero. Six zeros were `crashed-early` and 17 were `harness-error`; excluding these interrupted or failed attempts leaves 33 zero-score rows, of which 18 have a directory at the recorded capture path and 15 do not. Directory existence is not proof of a complete capture. These are **run-row and availability counts, not denominators for any failure mechanism**. Reruns and revisions are distinct attempts, not independent replications of an identical system. Old archives may exist elsewhere; only recorded paths were checked. Historical L4 traces are unavailable at their recorded paths.

## Handoffs, attention and consequences

### Java: false review failure and unrelated goal

The Java first reply batches a directory listing, `pom.xml` read, presumed edits and an incomplete replacement importer before seeing any of the read results. This is a failure of action integrity before the first checkpoint, independent of later compaction.

The compaction proxy's `0017-proxy.response.json` claims that creating `REVIEW.md` failed because it already existed. The later `0023-self-compact.response.json` repeats that failure, while also including the original importer task and an inventory showing `REVIEW.md` present. The original task was already present in that `0023` summary, yet the false failure persisted; supplying the task alone is therefore not a complete fix for unsupported status claims. At `0028-coder-s1.response.json`, the coder explicitly reasons that review creation failed because the file existed and emits a write for an unrequested `create_review_md_script.sh`, alongside another importer rewrite. A recorded file being present does not itself prove a correct review; it does contradict the proposed explanation that creation was necessary merely to get a file present. The campaign owner reports the underlying creation-failure assertion was false; verifying the exact original write receipt against the full chronology remains separate from the selected responses inspected here.

Later, `0038-coder-s1.prompt.txt` retains the original importer request but includes an explicitly unverified continuation and a `⟦ctx:rollup⟧` that both describe fetching Copilot versions through a GitHub rate limit as the task or primary outstanding requirement. In `0038-coder-s1.response.json`, the coder adopts that aim and issues `printenv | grep -E 'GITHUB_TOKEN|AUTH_TOKEN'`; `0039-coder-s1.response.json` then searches for missing token environment variables. This is observed task-purpose drift and a resulting action, not merely a keyword match. The delivered handoffs provide a plausible path for the noise to gain authority, but this observation does not establish the noise's first origin, that a different handoff would prevent drift, or the share of the final outcome caused by it.
