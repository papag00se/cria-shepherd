## Open — completion marks: what is still not known (2026-11-01, wave 10 MARKS)

**Built since the OVER entry** (`cria/completionmarks.py`, `gatecleanup`, `probegate`, `writeproxy`, `wsview`; see the last section of [check-evidence-custody.md](check-evidence-custody.md)): (1) the mark query now rides every carrier that can ask, not only the next write/edit program. The completion gate's worker reads the marks of the session's unreplied writes BEFORE the checks start and AFTER they end and declares both in the completed transport's own metadata (`bounds.marks`, never in checker output): a witnessed `did_not_run` is a proven unlanded call (`GuardState.gate_marks` -> `denial.unlanded_call_ids(..., extra)`), a mark final before the checks leaves a verified tree, and anything else (no mark: running, killed or never started; or one that appeared only while the checks ran) is an UNSETTLED write - the gate is partial (`gate_is_partial`), the clean reading is not recorded, and completion is held with a typed notice naming the file (`prompts/gate_unsettled_writes.txt`), bounded by `MAX_COMPLETION_CHECKS` like the unknown-evidence veto. A `read_file` / `list_dir` lowered while something is outstanding carries a body-less survey-kind record whose typed `pm` report is the same read-back (`wsview.marks_ride`; composed only when something is outstanding, otherwise byte-identical). (2) The gate releases the marks cria has already learned through the authenticated reader and retires its own empty certified directory through the owned retirement (never a prefix scan, never while a writer is outstanding). (3) The sentinel declares each write's mark nonce (`cm`), so `represent_inbound` re-derives the unresolved registry from the history after a restart (`completionmarks.adopt`).

**Still open.** (a) Reads and listings only: a `web_fetch`, a search, a native shell command and a MCP/other-tool next action carry no query (no wrapper is added to native commands; a fetch's first line is not guaranteed to be a record, and the survey slot after it would be text). The write/edit programs, reads, listings and the gate are the carriers. (b) What a restart still loses: the in-process `GuardState.gate_marks` (a gate witness that no history record repeats; the next gate or write program re-reads the mark), marks of calls older than the newest 64 (release is queued for the newest only; older ones stay in the private 0700 directory until the TMPDIR is cleared), and any write whose call never appeared in a re-presented history (composed, never run, never reported). The marks of calls first learned at the LAST gate also remain (released at no later program). (c) A writer that is killed or never started stays `incomplete` for ever, so the gate hold repeats up to `MAX_COMPLETION_CHECKS` times even after the coder rewrote the file (the rewrite waits the bound for it and says `late`, which the doctrine already reads as an unestablished touch): there is no way to tell a dead writer from a slow one. A superseded-by-later-landed-write rule was written and removed: a later write that is not `late` has by construction seen the earlier writer's mark, and one that is `late` does not settle it, so it never fired. (d) **Measured on a real coder, n is tiny - no rate, no win claim.** Real sandboxed Codex 0.159.3 (`suite.run` helpers) against a scratch cria, ornith1.5_9b; task: create `hello.py` and `NOTES.md`, run `hello.py`, say done; a `python3` shim in the sandbox PATH makes the FIRST lowered write program of the run hang before it starts (no mark, no reply), the coder's other call is parallel. ## Closed (2026-11-01, measured): a command cria composes cannot exceed 128 KiB — and the model's own write does not reach it

**The bound.** The harness runs `bash -lc "<command>"`, so every command cria composes is ONE argv string, and Linux caps a single argument at `MAX_ARG_STRLEN` = 32 pages = 128 KiB. Nothing inside the command escapes it — a heredoc, chunked printfs and base64 are all bytes in that same string. Codex reports the overrun as `Argument list too long (os error 7)` and fails the WHOLE exec. The fetch spill (`writeproxy._spill_command`) was where it was observed and it states its own bound (`SPILL_CONTENT_MAX`) and cuts with disclosure.

**The unmeasured path, now measured.** `writeproxy._write_command` — the model's own `write_file` — has ~13 KB of fixed program plus 4/3 base64, so its ceiling is ~88 KB of content. Census of every capture under `~/.cria/calls` (703 sessions, streamed file by file): **6,161 well-formed `write_file`/`edit_file`/`apply_patch` calls (2,845 / 2,959 / 357); the largest was 21.7 KB and none reached 24 KB.** The only calls past 24 KB were nine of the 31 calls whose arguments do not parse as JSON — runaway generations (the 150,895-byte `write_file` is one repeated `test(...)` block, `finish_reason: length` at 39,490 tokens) — and those never reach `_write_command`: a `length` reply is refused before lowering and the coder is told to build the file in pieces (`0013-coder-s1-continue1` in that session is exactly that message).

**The real-harness check.** Real Codex 0.159.3 (suite sandbox helpers, throwaway workspaces) through a scratch cria on the 3080's ornith1.5_9b, on tasks that demand a 100 KB+ file in one write. Task 1 (3,000 literal CSV rows): no write in 25 minutes — the generation-runaway guard aborted the reasoning five times in the first eight calls (`rumination hits=152`, `degenerate chars=30765`). Task 2 (a 1,500-entry, ~150 KB glossary): two complete, valid `write_file` calls of **28,008 and 28,015 bytes of arguments** (268 entries each, `finish_reason: tool_calls`, 7,008 / 5,995 completion tokens; opened in full, ends cleanly at `Zip file`) — the coder wrote about a fifth of what was asked and stopped on its own. So an 88 KB write is not what the coder produces even when told to, and output beyond ~30 KB is cut by cria's own guard; the unattributable failure is out of reach here, not merely unobserved. (n=2 tasks, two valid writes: a bound on what this model does, not a rate.)

**What was NOT built, and why.** No chunked/externalized write guard: nothing reachable to guard (0 of 6,161), and a guard would be an ADD against #15. What was added: the docstring now states the measurement, and `tests/write_edit/test_write_edit_notes.py::test_a_model_write_far_past_the_largest_one_ever_observed_still_fits_one_command_and_lands_exactly` pins that an 88 KB write (4x the largest observed) is a single command under 128 KiB that lands byte for byte through real bash, failing if the program's fixed overhead grows enough to eat the headroom (seen to fail with 30 KB of added program text). **Reopen if** a walked run ever shows `os error 7` on a `write_file`.

## Open: cria has no concept of PROGRESS — the diagnosis holds, the obvious fix measured inert (2026-09-18)

Walked on the first two `ternary-bonsai-2` L5 cells (`shipping-rates-rb` 5%, `cart-billing-go` 0%).
Across ~54 model calls the coder wrote **one file** (a Gemfile) and never touched a task file.

**The diagnosis, verified three ways in the source and not in doubt:**

1. `cria/prompts/coder_system.txt:5` says *"RESEARCH & INVESTIGATE FIRST … READ its real source/docs
   before writing code against it."* A grep of every prompt finds **no counterweight** — nothing tells
   the coder when investigation is finished.
2. `⟦ctx:facts⟧` records *"FILES YOU HAVE ALREADY READ"*. There is no counterpart for a conclusion
   reached or a change shipped, which is why the one-line `>` → `>=` fix was re-derived at calls 6, 7,
   9 and 26 of the same run and written zero times.
3. Every nudge in [heuristic-assists.md](heuristic-assists.md) keys on **repetition** (same tool+args
   ×3, same file rewritten ×5) or **doubt**. `unexecuted_write` needs file content in prose;
   `leg0_nudge_step` needs *zero* tool calls. A coder taking nine *different* read actions matches
   nothing in the arsenal.

So a coder that reads forever with varied arguments is invisible, and the rumination guard — the only
thing that ever fires — prescribes *"prefer reading the current file"*, which is the same blind spot
written as advice.

**The fix that follows from it, and MEASURED INERT.** Replace the guard's generic remedy with a true
progress fact cria already holds (the gate's failing `file:line`, turns elapsed with no write, and
whether that file changed). Replayed against the live model on the real captured call

| notice | writes | touched a task file |
|---|---|---|
| as sent (*"prefer reading the current file"*) | **0/4** | 1/4 |
| progress fact | **0/4** | 1/4 |

it moved the read from `Gemfile.lock` (irrelevant) to `lib/shipping/rates.rb` (the file to fix) — and

REFUSED*.** What was measured is one notice wording, on one guard arm, on one turn, of one cell, with
