- **What to do about the `retrospective` lens's CPU and its ~6,700-token ceiling (item 28; evidence in the decision-log).** Measured 2026-11-01 on 961 real texts (653 captured validation candidates, 308 writer outputs): every captured validation candidate was at most 2,672 rendered tokens; only writer outputs go longer (57 exceed the ceiling, 20 exceed 9,400). Chunking and cutting disagree with the full-text verdict too often (chunk any-`PLAN` 7 of 28, structural cut 3 of 15), and the full-text verdict is itself within 3 logits of a tie on 3 of 14 inputs over 2,400 tokens. Options: (a) leave it (a briefing over ~6,700 tokens is refused, fail closed, as today; no captured validation candidate has been that long); (b) retrain/replace the lens with a smaller graph or on long inputs (the only way to cut CPU without changing verdicts; operator-owned artifact); (c) accept the chunked judgment (about 1.3-2x less CPU at 3-4K tokens, ~25% different verdicts) - not recommended on this evidence; (d) add a cheap pre-flight refusal at the measured ceiling (saves the allocator's ~7 s of CPU and a ~13 GB RSS spike on a >7K input; changes no verdict) — **DONE (2026-11-02)**: `system1.token_ceiling` / `System1OverCeiling`, see docs/system1.md; (a)-(c) remain the operator's.
- **Write and edit results under more than 5 KB of shell noise (item 16b).** Codex keeps the first and last 5,000 bytes of a result; with 7 KB of noise before the program the record sits in the tail and is vouched for only by a declared second (survey) record that follows it. The real-Codex runs at 7,000 bytes per command (about 14 KB measured) showed every write and edit result UNKNOWN because those programs declared no survey: the files were right, the proof was absent. Options: (1) accept record 1 past a cut when it is the LAST thing in the result (a write/edit program prints nothing after it; a quoted record in a command's tail would still need this call's receipt, which is a correlation token, not a secret); (2) make every write/edit program print a trailer record at its very end (a tail always holds the end of the output), which changes every producer and the sentinel; (3) leave it: the survey, the gate and the completion marks already catch a missing write, and 7 KB per command is an extreme environment. Evidence: the real-PTY grid and the runs in item 16. Not decided here because (1) widens what a position-only proof accepts.
- **Nothing closes an image session in a running cria** (item 19a). Evidence: `ImageStore.release`/`confirm_close` are reached only from `cria.retention`; `ImageStore.session` keeps every session in `_sessions`/`_all` and each holds one open directory fd (`imagepersist.Hold`, a shared flock) plus its records in memory for the life of the process; the holder is skipped by `retention` by design, so `auto_prune_after` never reclaims a session the running process still holds. With `tools.workspace_image_tool` set, `ConfiguredImages.capture` opens a session for EVERY session key that offers the tool, image or not. On this machine `~/.cria/images` is empty and the fd limit is 524,288, so nothing is exhausted today (cost is fds, memory and disk per session key, unmeasured under load). Options: (1) leave it and document the cost (no change in authority); (2) let `AutoPruner` reach the live store and close sessions untouched for `auto_prune_after` through `ImageStore.release` (the configured age is already the deletion authority for the on-disk case; the open risk is a conversation resumed after the age, which then gets the typed unavailable path for its images); (3) open a session only when an image is actually present (not for every key when the workspace tool is merely offered), which shrinks the population without closing anything. Idleness/LRU eviction is excluded by the doctrine (no trusted close signal, measured with Codex 0.159.3). Implemented: nothing.
