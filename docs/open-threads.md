## Decisions awaiting the operator

- **What to do about the `retrospective` lens's CPU and its ~6,700-token ceiling (item 28; evidence in the decision-log).** Measured 2026-11-01 on 961 real texts (653 captured validation candidates, 308 writer outputs): every captured validation candidate was at most 2,672 rendered tokens; only writer outputs go longer (57 exceed the ceiling, 20 exceed 9,400). Chunking and cutting disagree with the full-text verdict too often (chunk any-`PLAN` 7 of 28, structural cut 3 of 15), and the full-text verdict is itself within 3 logits of a tie on 3 of 14 inputs over 2,400 tokens. Options: (a) leave it (a briefing over ~6,700 tokens is refused, fail closed, as today; no captured validation candidate has been that long); (b) retrain/replace the lens with a smaller graph or on long inputs (the only way to cut CPU without changing verdicts; operator-owned artifact); (c) accept the chunked judgment (about 1.3-2x less CPU at 3-4K tokens, ~25% different verdicts) - not recommended on this evidence; (d) add a cheap pre-flight refusal at the measured ceiling (saves the allocator's ~7 s of CPU and a ~13 GB RSS spike on a >7K input; changes no verdict).
- **Nothing closes an image session in a running cria** (item 19a). Evidence: `ImageStore.release`/`confirm_close` are reached only from `cria.retention`; `ImageStore.session` keeps every session in `_sessions`/`_all` and each holds one open directory fd (`imagepersist.Hold`, a shared flock) plus its records in memory for the life of the process; the holder is skipped by `retention` by design, so `auto_prune_after` never reclaims a session the running process still holds. With `tools.workspace_image_tool` set, `ConfiguredImages.capture` opens a session for EVERY session key that offers the tool, image or not. On this machine `~/.cria/images` is empty and the fd limit is 524,288, so nothing is exhausted today (cost is fds, memory and disk per session key, unmeasured under load). Options: (1) leave it and document the cost (no change in authority); (2) let `AutoPruner` reach the live store and close sessions untouched for `auto_prune_after` through `ImageStore.release` (the configured age is already the deletion authority for the on-disk case; the open risk is a conversation resumed after the age, which then gets the typed unavailable path for its images); (3) open a session only when an image is actually present (not for every key when the workspace tool is merely offered), which shrinks the population without closing anything. Idleness/LRU eviction is excluded by the doctrine (no trusted close signal, measured with Codex 0.159.3). Implemented: nothing.
- **Automatic retained-state cleanup** (`e77b1087`): exists, OFF by default. cria has no trusted session-close signal (measured with real Codex 0.159.3: nothing is sent at exit, `/clear`, `/quit`, SIGINT/SIGTERM or compaction), so it never infers closure from idleness. To enable, set `[retention] auto_prune_after = "14d"` (minimum `1h`; optional `auto_prune_every`, default `1h`) in `~/.cria/cria.toml`; that setting IS the deletion authority. Choose an age longer than any conversation you will resume. Not enabled live. Linked: closing live image sessions by the configured age needs the pruner to reach the live store (item 19a).
- **Re-adjudicate "withhold a steer that contradicts the session's own response shapes"** (refused twice on the 98-run corpus; counter-evidence 2026-08-04: two ledger-disprovable steers/plan steps that arrived BEFORE the write they caused). If revisited, the fix belongs in the steer author's prompt (fence it to the parsed field names), not in a downstream deletion; re-open only with >=5 runs on current code showing the false claim still happens (decision-log).
- **Two elision roots left to the operator:** `content_reduce.INLINE_RESULT_MAX_BYTES = 9000` still bounds eleven model-facing paths and cria's own source calls the belief behind it "outlived its evidence" (measure it from the wire, as `note_harness_cuts` already asks, or keep remembering it); and `toolmenu.focus_tools` drops a harness's native search, which in a deferred-tool harness removes the model's only route to most tools.
- **`searches_match` trigger:** ask the existing `search_rehunt_judge` question for every earlier non-literal search, refuse only on a repeat verdict, admit when the judge is silent? Measured on 667 real searches: it would put a reasoner call on 475 of them (+232, about 2x), 23 of 40 sampled non-matches read as repeats by the judge (missed repeats cost wasted searches, not wrong refusals), and the judge is unstable on version bumps (2-6 of 8 new-direction on identical input). Owner `semanticquery.rehunt` + `researchpolicies.search_admission`/`webfetch` deny record (hot files); `gate_search` has no deny path, so this is a redesign.
- **Progressive text for proxy turns at the live configuration** (item 14): drop `metrics` / move the banner and note lines after the text for streamed turns, or keep buffering.
- **A protected read that leaves the reply less than the floor's reply room** (item 30). (a) Treat it as `ReadFitOverflow` when `window - real < reply_room_floor`: the coder gets the existing narrower-pieces guidance, never a 7-token reply; it also refuses reads that today squeeze through with a few hundred tokens (the real 363-token reply on a 24K server succeeded, 41% of real coder replies are longer than 363). (b) Refuse only below a hard minimum that cannot hold a tool call (an invented number: 64? 256?). (c) Keep the squeeze and say so (a labelled note on the oversize result) so the coder can ask for a narrower read. Evidence for choosing: 2 of the 3 real squeezes under 1,024 tokens were truncated, the 7-token one four times in a row.
- **Should the context floor be a registered, removable assist?** Today `Upstream._prep` gates `contextfloor.fit` on `engagement_level >= CONTEXT_FIXES` (L3) and nothing in the registry or `LEVELS.md` records that rung; its level matrix is proved only through the real server (`test_the_context_floor_runs_exactly_at_l3...`). It cannot simply be registered like the other level-gated options: `build_report.validate` forbids a definition in F68 (`required_wire_contract`: "no disabled/per-helper fit mode exists", docs/shephard.md), and a registered definition becomes opt-out-able through `[assists] disabled` and the ablation profiles. Options: (1) leave it a required foundation gated by `config.CONTEXT_FIXES` (status quo; the test above guards the rung); (2) register a rung-only record for it, a new definition in a non-F68 family that `Upstream._prep` reads, accepting that `[assists] disabled = ["context-floor"]` then turns off the floor (the operator can already break a fit by a small `context_size`, but never by an opt-out list); (3) add a `required` marker to `Policy` so a foundation appears in `LEVELS.md` at its rung but `validate_selection_ids` rejects it in `disabled` (smallest change to the doctrine that keeps F68 non-removable, but a new field on every policy). Implemented: nothing; `Upstream._context_fixes` also gates unrelated wire folds at L3, which a registration would have to split.
- **A user prompt that quotes a `⟦cria⟧ ` line loses it** (`indicators.strip_history` strips them from every user/assistant message; tool results are exempt). Evidence (AUDREORG2, 20,848 captured Codex requests): 565 distinct user messages carry such a line and ALL 565 are the harness compaction turn (it stores cria's reply banner inside the preamble message); no real user prompt quoted one, so the cost is zero so far. Options: (a) keep (a user pasting cria's own output loses those lines; also the only safe rule for a harness that REPLACES the root with the summary, not captured); (b) strip user-role lines only in a message that carries the harness preamble or is not the first user message, and keep them elsewhere (needs a root-replacing harness capture before it is safe).
- **`merge_for_alternation` shape change, the post-compaction typed survey instead of an authored steer, and the suite install directory name** are decisions inside items 8, 1 and 15 above.
