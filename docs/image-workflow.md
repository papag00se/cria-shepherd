# Image observation and reinspection

Image viewing uses the model role that actually serves the turn, not a separate judge. That is normally the coder; the classifier sends question-class turns ("what does this image say?") to the reasoner, so declare the same `vision`/`vision_model` on `[roles.reasoner]` when it serves the same backend (a role without its own declaration never views images). Vision capability defaults to unknown. To opt in, merge these settings into the existing operator configuration, using the exact model identity resolved by the configured HTTP backend:

```toml
[roles.coder]
backend = "existing-http-backend"
vision = true
vision_model = "<exact wire model id>"
```

The backend table must already exist. For a served backend, the pin must match its `/v1/models` identity; for a keyed backend, it must match its configured wire model. A harness alias does not supply capability. Unknown, false, missing discovery, different providers/models, CLI backends and unresolved routes cannot authorize an image POST. `vision = true` requires a nonempty string model pin. Changing models requires deliberate configuration of the new identity.

Workspace reinspection has a separate, default-unbound harness contract. Only when the operator knows this deployment uses the native `view_image(path)` harness tool should they declare:

```toml
[tools]
workspace_image_tool = "view_image"
```

Merge this into an existing tools table rather than duplicating it. A request must also offer that tool with a compatible string `path` schema. A matching client name, schema, marker or path-shaped text alone never binds the contract. Other native contracts are currently unsupported. Attachment observation does not require this workspace declaration.

The original image remains private until a completed observation is correlated with its exact occurrence, selected provider, applied coder role/model and actual image-bearing POST. Subsequent coder context contains a labelled historical account, extracted text, uncertainty and a reinspection reference. It does not claim the account is verified perception. Task/root packets and unrelated tool history are preserved; projection happens only in the prepared model view.

For a retained attachment, `reinspect_image` sends the original source to the same coder again. For a workspace reference, it emits a fresh native read for the harness to execute. The returned image becomes a new occurrence and observation; the server does not read the workspace locally or silently reuse old pixels as current file contents. Data URLs retain their encoded source; remote URLs remain references rather than frozen remote bytes.

Private producer-issued call IDs correlate exact issued actions with returned result packets. They are not authentication credentials: the operator declaration does not authenticate an arbitrary API caller or independently prove that a harness executed a read. Observations remain labelled accounts of the image bytes reported by the harness. Duplicate, changed, unregistered or unsupported result structures are explicit errors.

Image token cost remains explicitly unknown when native measurement cannot establish it. No text-density estimate proves visual fit. Protected multipart reads settle only after their final full model request is measured and delivered; a prior image observation gives them no read credit. An unknown fit outcome preserves the received carriers without credit; a measured overflow withholds the encoded transport pages and tells the coder the file size and how to read it in narrower pieces, also without credit.

Reads and the retention of private state are documented in [reads-and-retention.md](reads-and-retention.md).

Chat text SSE remains token-progressive, including when an image tool is offered; the Responses wire is fake-streamed (created first, then one delta per item once the completion exists) except for the narrow token-progressive subset in [open-threads](open-threads.md) (never an image-bearing request, which always buffers). Image-bearing requests buffer their internal observation/reinspection exchanges before emitting the final completion; the harness receives a complete, valid event stream (Responses: created, in_progress heartbeats, output item/content events, completed; Chat: keepalive comment, role chunk, content chunks, stop, `[DONE]`). Validated against a real vision model (gemma4_12b with its projector) through a scratch cria: Responses and Chat streaming with an image attachment, a text-only stream in the same server, and a real sandboxed Codex 0.159.3 using its native `view_image` tool (schema `{path: string}`, required, no additional properties). A changed file between two reads produced a fresh observation from the new bytes, and only the two observation requests carried pixels.

A Codex deployment must declare image input for the served model in its model catalog (`input_modalities` containing `image`). The suite's restored launcher (`suite/run.py::local_codex_catalog`) declares `image` exactly when the cell's cria config has `[roles.coder] vision = true`; every other cell keeps the byte-identical text-only catalog. With a text-only catalog Codex itself refuses to execute `view_image` ("not allowed because you do not support image inputs") and cria passes that refusal text on to the coder as the tool's own result; no observation exists then.

An `http(s)` image URL is a reference, never fetched by cria: it is passed to the vision-capable backend unchanged (the backend, not cria, fetches it), the observation is labelled as made from a remote URL reference with no retained copy, and reinspection asks the backend to view the URL again. Without a declared vision role the request is refused with an explicit `image_unavailable`; the image is never dropped silently.

Completion judges and critics read an observed image packet (including a harness `view_image` result) as its labelled observation, the same text the coder sees, never as pixels or as nothing. An image the user ATTACHED to the task lives in the task message, not the action log, so the satisfaction judge receives its labelled observation as its own evidence block (`satisfaction_image_observation`, attachments only; a tool-result packet is already in the log). Before that block existed the judge was told to check the reply against an observation that was not in its evidence, and ruled 'no observation of an image'. The closing file-based confirmation (`list_dir`/`read_file`) cannot verify an account of image contents, so for a whole task it is skipped only when two source-owned facts agree: the request holds an image occurrence with a completed, correlated observation (the store's record, never message text), and one focused reasoning-on question answers that carrying out the task writes or changes nothing on disk. A task that also asks for a file, an image without a completed observation, no reasoner role, or an unreadable answer keeps the full confirmation. The coder's closing reply is the deliverable of such a task, yet the action log never holds it (the reply is the completion being judged). For a plan-off done claim it is therefore passed to the satisfaction judge as a labelled claim (`satisfaction_closing_claim`), only when the request holds an observed image occurrence (the same typed provenance); the judge is told the observation is the only evidence of what the image shows and must check the reply against it. A reply the observation contradicts or embellishes is not accepted, and with no observation the reply is not shown to any judge, so an ungrounded claim about an image stays unaccepted. Scheduled and plan-on reviews do not carry the reply (planning is off by policy; a scheduled review has no closing reply to carry). A statement deliverable with NO image rides the same way (`satisfaction_closing_claim_statement`, `loop._statement_deliverable`): when the whole transcript is present and `writerecord.WriteRecord` shows nothing that wrote or could have written, one reasoning-on deliverable-type question (`confirm_applies`, once per task per session) decides whether the task needs a file; NO makes the reply the deliverable, checked against the action log's tool results, and the whole-task file confirmation (which cannot confirm a statement) is skipped for that approval. YES, an unreadable answer, a write in the transcript, a compacted transcript or any image occurrence keeps the unchanged evidence and confirmation.

Retained image sessions (private state under `${XDG_STATE_HOME:-~/.local/state}/cria/images`) follow the same rule as every retained private state: cria deletes nothing unless the operator runs `python -m cria.retention prune` or sets `[retention] auto_prune_after`; a conversation that continues after its image session was pruned is not restorable and never gets a fabricated observation. See [reads-and-retention.md](reads-and-retention.md#retention-nothing-is-deleted-unless-the-operator-says-so).
