# Image observation and reinspection

Image viewing uses the model role that actually serves the turn, not a separate judge. That is normally the coder; the classifier sends question-class turns ("what does this image say?") to the reasoner, so declare the same `vision`/`vision_model` on `[roles.reasoner]` when it serves the same backend (a role without its own declaration never views images). Vision capability defaults to unknown. To opt in, merge these settings into the existing operator configuration, using the exact model identity resolved by the configured HTTP backend:

```toml
[roles.coder]
backend = "existing-http-backend"
vision = true
vision_model = "<exact wire model id>"
```

The backend table must already exist. For a served backend, the pin must match its `/v1/models` identity; for a keyed backend, it must match its configured wire model. A harness alias does not supply capability. Unknown, false, missing discovery, different providers/models, CLI backends and unresolved routes cannot authorize an image POST. `vision = true` requires a nonempty string model pin. Changing models requires deliberate configuration of the new identity.

Workspace reinspection has a separate, default-unbound harness contract. Only when the operator knows this deployment uses the native `view_image(path)` harness tool should they declare:

```toml
[tools]
workspace_image_tool = "view_image"
```

Merge this into an existing tools table rather than duplicating it. A request must also offer that tool with a compatible string `path` schema. A matching client name, schema, marker or path-shaped text alone never binds the contract. Other native contracts are currently unsupported. Attachment observation does not require this workspace declaration.

The original image remains private until a completed observation is correlated with its exact occurrence, selected provider, applied coder role/model and actual image-bearing POST. Subsequent coder context contains a labelled historical account, extracted text, uncertainty and a reinspection reference. It does not claim the account is verified perception. Task/root packets and unrelated tool history are preserved; projection happens only in the prepared model view.

For a retained attachment, `reinspect_image` sends the original source to the same coder again. For a workspace reference, it emits a fresh native read for the harness to execute. The returned image becomes a new occurrence and observation; the server does not read the workspace locally or silently reuse old pixels as current file contents. Data URLs retain their encoded source; remote URLs remain references rather than frozen remote bytes.

Private producer-issued call IDs correlate exact issued actions with returned result packets. They are not authentication credentials: the operator declaration does not authenticate an arbitrary API caller or independently prove that a harness executed a read. Observations remain labelled accounts of the image bytes reported by the harness. Duplicate, changed, unregistered or unsupported result structures are explicit errors.

Image token cost remains explicitly unknown when native measurement cannot establish it. No text-density estimate proves visual fit. Protected multipart reads settle only after their final full model request is measured and delivered; a prior image observation gives them no read credit. An unknown fit outcome preserves the received carriers without credit; a measured overflow withholds the encoded transport pages and tells the coder the file size and how to read it in narrower pieces, also without credit.

A multipart read is atomic with respect to writers. The first page command reads the source once (one descriptor, `fstat` before and after, length checked against the size). When the stream needs more pages it copies those very bytes into a private snapshot (`snap`, plus `meta` holding the identity taken) inside an authenticated owned directory `.cria-mpsnap-<token>` under the harness's own `$TMPDIR` (`ownedfiles.DIRECTORY_PROGRAM`, the capability the edit-sequence and gate scratch use), re-reads the copy through its owned name and compares its digest with the bytes it was written from. Every later page is served from the snapshot, never from the path, so the logical read is exactly the file as of the first page whatever a writer does between pages (rewrite in place, append, truncate, replace by rename, change and revert); a snapshot altered in place changes the digest each page reports and the consumer, which compares every page's source and stream digests with the first page's, fails the read closed as unverified. Each page record carries a typed `snapshot` object: `mode` (`snapshot` or `live`), `reason` (`over_cap`, `unavailable` or none), `taken` (device, inode, size, mtime_ns when the snapshot was taken) and `now` (the path's identity as of that page). If the identity at the LAST page differs from the one taken (or the path is gone), the read is still delivered, as the first page's exact bytes, but labelled (`⟦ctx:read-source-changed⟧`, from `prompts/multipart_source_changed*.txt`: the file changed after the read began, what it is now, read it again before relying on or editing it); the label rides after the record, so the result earns no read credit and no protected-read fact (never current). A change that restores the mtime as well leaves identical bytes under an identical identity and is not reported: the delivered bytes are then the file's. The page that carries the last extent removes the snapshot; an abandoned read leaves it, and only the operator removes it (`python -m cria.retention list|prune --kind snapshot [--tmp DIR] --older-than ...`, never part of `--kind all`; there is no session-close signal to sweep on). A re-run first page replaces its own earlier snapshot. A source larger than `filecommands.MULTIPART_SNAPSHOT_MAX_BYTES` (the bytes the reference window holds at the repo's chars/4 estimate: a larger file cannot be delivered whole to that window anyway), or a snapshot that cannot be made (unwritable `$TMPDIR`), is paged live with the typed reason in the record: the earlier hash- and metadata-checked, detect-and-fail-closed behaviour, which cannot see a change-and-revert. The identity comparison happens when the last page runs, not when the model reads the result. Reflink (`FICLONE`) is not used: the first page's bytes are already in hand from the one descriptor and a clone could only be hashed against them again.

Chat text SSE remains token-progressive, including when an image tool is offered; the Responses wire is fake-streamed (created first, then one delta per item once the completion exists) except for the narrow token-progressive subset in [open-threads](open-threads.md) (never an image-bearing request, which always buffers). Image-bearing requests buffer their internal observation/reinspection exchanges before emitting the final completion; the harness receives a complete, valid event stream (Responses: created, in_progress heartbeats, output item/content events, completed; Chat: keepalive comment, role chunk, content chunks, stop, `[DONE]`). Validated against a real vision model (gemma4_12b with its projector) through a scratch cria: Responses and Chat streaming with an image attachment, a text-only stream in the same server, and a real sandboxed Codex 0.159.3 using its native `view_image` tool (schema `{path: string}`, required, no additional properties). A changed file between two reads produced a fresh observation from the new bytes, and only the two observation requests carried pixels.

A Codex deployment must declare image input for the served model in its model catalog (`input_modalities` containing `image`). The suite's restored launcher (`suite/run.py::local_codex_catalog`) declares `image` exactly when the cell's cria config has `[roles.coder] vision = true`; every other cell keeps the byte-identical text-only catalog. With a text-only catalog Codex itself refuses to execute `view_image` ("not allowed because you do not support image inputs") and cria passes that refusal text on to the coder as the tool's own result; no observation exists then.

An `http(s)` image URL is a reference, never fetched by cria: it is passed to the vision-capable backend unchanged (the backend, not cria, fetches it), the observation is labelled as made from a remote URL reference with no retained copy, and reinspection asks the backend to view the URL again. Without a declared vision role the request is refused with an explicit `image_unavailable`; the image is never dropped silently.

Completion judges and critics read an observed image packet (including a harness `view_image` result) as its labelled observation, the same text the coder sees, never as pixels or as nothing. An image the user ATTACHED to the task lives in the task message, not the action log, so the satisfaction judge receives its labelled observation as its own evidence block (`satisfaction_image_observation`, attachments only; a tool-result packet is already in the log). Before that block existed the judge was told to check the reply against an observation that was not in its evidence, and ruled 'no observation of an image'. The closing file-based confirmation (`list_dir`/`read_file`) cannot verify an account of image contents, so for a whole task it is skipped only when two source-owned facts agree: the request holds an image occurrence with a completed, correlated observation (the store's record, never message text), and one focused reasoning-on question answers that carrying out the task writes or changes nothing on disk. A task that also asks for a file, an image without a completed observation, no reasoner role, or an unreadable answer keeps the full confirmation. The coder's closing reply is the deliverable of such a task, yet the action log never holds it (the reply is the completion being judged). For a plan-off done claim it is therefore passed to the satisfaction judge as a labelled claim (`satisfaction_closing_claim`), only when the request holds an observed image occurrence (the same typed provenance); the judge is told the observation is the only evidence of what the image shows and must check the reply against it. A reply the observation contradicts or embellishes is not accepted, and with no observation the reply is not shown to any judge, so an ungrounded claim about an image stays unaccepted. Scheduled and plan-on reviews do not carry the reply.

There is no trusted session-close authority, so retained private resources are not deleted on request end, model completion, cache eviction, compaction or idle timeout. This was measured, not assumed: real Codex (pinned 0.159.3, `exec` and the TUI) sends no request at exit, `/clear` (the next turn simply carries a new `session-id`/`thread-id`; the old one is never mentioned again), `/quit`, SIGINT/SIGTERM cancel (the in-flight connection just drops) or compaction (an ordinary `POST /v1/responses` with `request_kind: compaction`, same `session-id`, an incremented `window_number`); Chat Completions clients can only supply `X-Cria-Session-Id`, a name with no close semantics. Operator call captures and backend caches have separate retention. Deletion authority is therefore the OPERATOR's, in one of two forms, both using the same selection and removal code: by default **nothing is deleted** and cleanup is an explicit act: `python -m cria.retention list` shows every retained multipart and image entry (size, age by last touch, state, kind) and `python -m cria.retention prune` removes entries only with `--apply` (dry run by default; it needs `--older-than 14d` and/or `--session ID`, optionally `--kind multipart|image`). The operator's invocation is the authority; cria never calls it, and idleness or age is the operator's judgment, not a close signal. Image sessions are removed through the store's own closed-seal path (seal outside the payload, payload, seal last), multipart state through its own lock file (session record first, then call associations); a live cria process holding an image session or the multipart lock is skipped, corrupt entries are only removed when selected by `--session`, symlinks and unrecognized names are never touched, and an interrupted run is retried by running it again. The second form is a standing instruction: set `[retention] auto_prune_after = "14d"` (minimum `1h`; default unset = off; optional `auto_prune_every`, default `1h`, minimum `1m`) and cria runs `prune --apply --older-than` on `multipart` and `image` state itself, once at start and then on that cadence, from a background daemon thread. It is the operator's configured age, not cria's inference of closure. It has every protection above (a held multipart lock or live image holder is skipped, corrupt entries are never removed automatically, only `--session` does that; symlinks and unknown names are refused), releases the multipart lock before touching images, logs one `retention.auto_prune.removed` / `.skip` / `.failed` event per entry (a skip is announced once per process), and cannot raise into request handling (any failure is contained and logged as `retention.auto_prune.error`). Source snapshots in the shared temp directory are never pruned automatically. A request in flight against state that is pruned gets the existing typed unavailable path, never a fabricated read; choose an age longer than any conversation you intend to resume. A conversation that continues after its state was pruned fails closed: removed multipart continuations yield the existing unverified/unavailable note and removed image sessions are not restorable, never a fabricated read. These checks catch mistakes, not authentication: any process running as the same user can forge or delete these files.
