# The project-local route cria offers when it refuses a machine-wide install, one per ecosystem.
# Model-facing (rule 22), keyed `<manager>_<route>`; dirguard._INSTALL_REMEDY picks the first route
# whose tools are actually on PATH.
#
# VERIFIED ON THE BOX, 2026-08-21, on the shipping-rates-rb seed: configuring the project path
# then running `bundle install` with a Gemfile naming ONLY `countries` installs in about a minute,
# and the suite then runs green under a plain `ruby -Ilib -Itest` — no `bundle exec` anywhere —
# because the library file's `require "bundler/setup"` puts the bundled gems on the path for whatever
# loads it. THE SAME ROUTE FAILS COMPLETELY if the Gemfile also names the test framework: the test file has
# already activated the system minitest by the time the library file runs, and `bundler/setup`
# raises `Gem::LoadError` rather than accept the mismatch, so every test errors before it runs.
# ternary-bonsai wrote exactly that Gemfile (`minitest "~> 5.18"` beside `countries "~> 1.2"`) on
# run 1787340410 and scored 1/5; the pin was the second killer, since countries 1.2 depends on
# `currencies`, which no longer builds. Both are now named in the route.
#
# A ROUTE CRIA HAS NOT VERIFIED IS A ROUTE CRIA IS GUESSING. Its executable must be resolved on
# the coder's PATH before it is named; otherwise cria refuses the shared install without inventing a
# command. That avoids answering a real command with an imaginary one (#5b).
#
# Every route below names the tools it needs, in code, and writes that tool back into its own
# sentence through a {{TOOL}} token. The presence check answers "is it there"; the token carries
# "what is it called". Splitting those two is how the ruby row came to be SELECTED on the
# strength of `bundle3.2` and PRINTED as `bundle`, which this box does not have — ten refusals,
# half a coder budget and collapsed the run (cycle 2, shipping-rates-rb x ternary-bonsai). When none of an ecosystem's routes are
# available the honest answer is the empty one: say what is forbidden and stop. That is already how
# apt, dnf, brew and pacman are handled — they install to the machine and have no project-local
# form, so no route is invented for them (#3).
#
# …AND HOW TO RUN A ONE-OFF COMMAND UNDER IT. The routes explain how to make a LIBRARY FILE
# loadable, which is what the tests run against. A coder checking something with a throwaway
# `ruby -e` / `python -c` goes through no library file and loads none of the install — and
# nothing here said so. Walked on `shipping-rates-rb x ternary-bonsai` 1787111689: the coder
# invented `BUNDLE_PATH=./vendor/bundle ruby -e "require 'countries'"`, got the same LoadError
# eight times, and the one time it typed `bundle exec` it worked — with the working form still
# in its own history.
# MEASURED before adding it (#15): across 139 captured sessions, 49 — **35%** — show a bare
# `-e`/`-c` one-liner co-occurring with a load error. Only the two ecosystems whose install is
# project-local and needs a launcher; node resolves from ./node_modules with no wrapper.
#
# AND A ROUTE MUST NOT NAME A PATH ITS OWN COMMAND DOES NOT CREATE. `gem_bundler` configures
# Bundler's project path, whose gems live under `vendor/bundle/ruby/<abi>/gems/…`; `vendor/bundle/gems`
# does not exist. That path
# came from a run that installed with `gem install --install-dir` — the OTHER route, where it is
# correct — and it only became reachable when ruby-bundler was installed, because
# dirguard._INSTALL_REMEDY takes the first route whose tool is on PATH. Installing an apt package
# flipped cria onto a route carrying a different route's path.
#
# The same sentence also asserted that a Bundler-path install is unreachable from plain `ruby`. Measured
# in a clean project: `require "bundler/setup"` plus `ruby -Ilib -e` from the project directory
# WORKS, and every check in shipping-rates-rb/verify.py runs `subprocess.run(cmd, cwd=ws)` — the
# project directory. It fails only from elsewhere, which BUNDLE_GEMFILE answers.

pip_venv = First check whether you need it at all: the package may already be importable, and `pip install -e .` or `pip install .` installs YOUR OWN project, which your script and tests do not need. If a third-party package really is missing, install it into the project: `{{PYTHON3}} -m venv .venv && ./.venv/bin/pip install <pkg>`, then run with `./.venv/bin/python`. That applies to a one-off check too — `{{PYTHON3}} -c "..."` uses the system interpreter and will not see it.

npm_local = Drop the global flag: `{{NPM}} install <pkg>` installs into this project's own `node_modules`, which is what your code will load.

gem_bundler = Install it into the project instead: add the gem to a `Gemfile`, run `{{BUNDLE}} config set path 'vendor/bundle'`, then run `{{BUNDLE}} install`. Gems installed that way are not on the default load path, so make them reachable from your LIBRARY FILE rather than from the command line: put `require "bundler/setup"` at the very top, before the gem require. That covers anything started from the project directory — including tests and scripts you did not write, which are what will be run against your code. A process started from somewhere else needs `BUNDLE_GEMFILE` pointing at your `Gemfile`. A one-off command that does NOT go through your library file — `{{RUBY}} -e "..."` to check something — loads none of it: put `{{BUNDLE}} exec` in front of that one. Put ONLY the gem you actually need in that `Gemfile`, and do not pin its version. Naming your test framework there is what breaks this: the test file loads it before your library file runs `bundler/setup`, and `bundler/setup` then refuses the version already in memory — `You have already activated minitest 5.16.3, but your Gemfile requires minitest 6.0.6` — which fails every test at once, including the ones you did not write. A version pin does the same damage a second way: an old release drags in dependencies that no longer build.

gem_direct = Install it into the project instead: `{{GEM}} install --install-dir vendor/bundle <gem>`, then make it loadable FROM YOUR CODE — `$LOAD_PATH.unshift` the gem's `lib` directory at the top of your library file, so it is on the load path for anything that requires it. Setting `GEM_HOME=vendor/bundle` only covers commands you launch yourself; tests and scripts you did not write are run without it, and those are what will be run against your code.

cargo_add = A crate your code uses is a dependency, not a global binary: `{{CARGO}} add <crate>` puts it in `Cargo.toml` and cargo fetches it into this project.

go_get = A module your code imports is a dependency, not a global binary: `{{GO}} get <module>` records it in `go.mod` for this project.

composer_local = Drop `global`: `{{COMPOSER}} require <pkg>` installs into this project's own `vendor/`.

maven_dep = A library your code imports is a dependency, not an install: add it to the `<dependencies>` block in `pom.xml` and let the build fetch it.

# THE FACT BEFORE THE ROUTE. cria resolves the binary to build the route's sentence, so when the
# coder tries to INSTALL that same tool cria already knows the answer. Walked on cycle 4 cell 13:
# `which bundler; gem install bundler` was refused with "run bundle3.2", which answers
# "install bundler" with "run bundler" — and the refusal swallowed the `which` that would have
# settled it. The coder never learned bundler was installed and spent the rest of the run on
# transport.
already_present = {{PACKAGE}} is already installed on this machine — the executable is named `{{TOOL}}`, so type that instead of `{{PACKAGE}}`. You do not need to install it.

# WHEN THE ROUTE IS NOT KNOWN YET, WHICH IS NOT THE SAME AS THERE BEING NONE. The routes above are
# chosen by asking which binaries are on the CODER's PATH, and that answer arrives on a workspace
# survey — so the first refusals of a session have nothing to offer. They used to say nothing at
# all, which reads as "this cannot be done": at 20260823T032555 the escalation reasoner read nine
# routeless refusals and told the coder to hardcode the data the gem would have provided, while the
# gem was installed on the box and the project-local form passed cria's own guard. 580 of 3,704
# renderings (16%) were routeless. This clause says which of the two is true (#23c).
route_unknown_yet = A project-local way to install this may well exist — which command this machine has is not established yet, so no exact one is named here. Do not conclude the package is unobtainable: install it INTO the project (a directory inside the workspace, e.g. `vendor/`, `.venv/`, `node_modules/`), not into the shared environment.
