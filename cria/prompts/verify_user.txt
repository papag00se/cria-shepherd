# The critic's USER message (the system instruction is verify.txt). It carries the step
# plus the REAL ground truth the critic judges. The parts are joined with a blank line
# between them; `evidence` and `probe` are dropped entirely when there's nothing to show.
# `\n` in a value becomes a real newline. Format is `key = value`, one per line.
step = STEP: {{STEP}}
evidence = WHAT THE CODER DID — its tool CALLS and what they returned (real ground truth):\n{{EVIDENCE}}
probe = GROUND-TRUTH CHECKS (lint · type-check · tests · git): {{PROBE}}
# Added when the checks came back RED. The checks run over the WHOLE repository, so a finding carries
# no information about WHICH step produced it — nothing in the check output attributes a failure to a
# step, and that attribution is a judgment, which is why it is asked here rather than pattern-matched.
# The findings are the checker's own lines WITHOUT the coder-facing "resolve exactly what it names"
# preamble: an imperative reads as a task briefing to a weak judge and it starts fixing instead of
# ruling. Stated as a fact plus ONE narrow question; it never suggests an answer in either direction.
probe_red = THE REPO'S OWN CHECKS ARE CURRENTLY FAILING. These checks run over the WHOLE repository, so this is a fact about the repository — it is NOT a verdict on this step, and the output cannot say which step's work produced it:\n{{FINDINGS}}\n\nThe ONLY question you are being asked about these failures is whether THIS step's own goal requires them to be resolved. If they are this step's own work failing — the code this step wrote does not parse, the tests this step wrote fail, the command this step runs errors — that is this step failing, so answer false and name it. If they are in work that a DIFFERENT step of the plan covers, they are not evidence about this step at all: judge this step on its own goal exactly as you would with clean checks. Someone else will decide whether the whole task is finished; do not answer that question here, and do not fix anything yourself.
summary = CODER'S SUMMARY (a claim — trust the tool output above over this):\n{{CODER_SUMMARY}}
# Restated LAST because the step is stated once, thousands of characters earlier, while the coder's
# summary routinely narrates its OWN numbered plan ("Step 3: write unit tests…") right before the
# verdict. A judge asked to rule on the nearest concrete step statement takes the coder's. Observed:
# the critic opened its reasoning with "The coder's step is 'Write unit tests…'" — the coder's Step 3
# — and judged a "read the API spec" step NOT DONE for having no tests. Same fact, no deletion, put
# where the ruling happens.
step_again = THE STEP YOU ARE RULING ON IS THE ONE AT THE TOP, RESTATED HERE — any step numbering inside the coder's summary is the CODER's own and is NOT what you judge:\n{{STEP}}
summary_leak = (the coder's completion message was a malformed tool call, not a summary — judge from the evidence above)
absent_literals = ON-DISK FACT, gathered by running the check — not a verdict, and not necessarily a failure: the step quotes {{LITERALS}}, and {{ARTIFACT}} does not contain {{THEM}} anywhere. Decide for yourself whether this step's goal needs them present. If the step asked for the artifact to USE those exact values, it does not yet.
# What has really been READ this session — web documents that DEFINED routes or response fields, and
# files on disk that came back with content. Gathered by cria (research.sources_read), never claimed:
# a page that answered while defining nothing is not here. This is the fact a critic ruling on a
# "research the API" step could not otherwise get — the transcript shows attempts, not outcomes.
sources_read = WHAT HAS ACTUALLY BEEN READ SO FAR (gathered from the real tool results — each of these returned content, and everything else that was tried did not):\n{{SOURCES}}\n\nIf THIS step's goal was to find something out, judge whether what is listed here answers it. If the step's goal was to BUILD something, this list is background and does not make it done.
